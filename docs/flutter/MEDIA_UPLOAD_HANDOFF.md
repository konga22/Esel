# 사진 업로드·조회 연결 (#30)과 남은 발행 작업 (#31)

## 먼저 읽을 결정: 사인 뒤로 업로드 보류

2026-10-19 사용자 확인. **사인 뒤로의 서버 업로드는 보류한다.** 이 효과는 사인 글자로 얼굴을 가리는데, #30의 사진은 사인 글자·캡션을 제외해서 보내야 한다. 글자를 빼면 가렸던 얼굴이 다시 드러날 수 있다.

- 사인 뒤로 단독과 사인 뒤로 + 물감 모두 서버 업로드를 차단한다. `SIGNATURE_UPLOAD_PENDING` 이유를 안내하고 다른 연출을 직접 선택하도록 한다.
- 앱 안 미리보기·로컬 발행·기존 기록은 유지한다. 임의로 다른 가림을 추가하거나 원본으로 우회하지 않는다. 익명화를 보장한다고 설명하지 않는다.
- 팀에서 글자를 제외한 사진의 저장·표시 방식을 합의하고 공개 사진 조회 경로까지 검증한 뒤 해제한다. **#31의 서버 DTO가 바뀌어도 이 보류가 자동으로 풀리는 것은 아니다.**

조원에게 전달할 문장:

> 사인 뒤로는 글자로 얼굴을 가리는 효과라, 글자를 빼고 사진을 올리면 얼굴이 드러날 수 있어 서버 업로드만 보류했습니다. 앱 안 미리보기와 로컬 기록은 유지합니다. 다른 연출을 직접 고르도록 안내하며, 이 효과를 서버에 어떻게 저장하고 보여 줄지 팀에서 정한 뒤 연결하겠습니다.

## 이번에 구현한 것

- `PublishPhotoRenderer`: 기존 얼굴 위치·자르기 계산과 물감 에셋으로 PNG 생성. 사인·캡션·원본 얼굴 좌표는 이미지 업로드에 넣지 않는다.
- `MediaUploadController`: 계정 소유권 → 보류 검사 → 사진 읽기 → 렌더링 → 업로드. 실패 시 원본으로 재시도하지 않는다.
- `MediaRemoteSource`: 준비 POST → 사진 바이트 PUT → complete의 READY 확인. 외부 업로드 URL 거절. 기존 HTTP 인증·토큰 갱신·오류 처리를 사용한다.
- 서버가 준 media ID로 홈·팔레트·스케치북·상세·로그인 맛보기 배경을 연결한다. 격자는 thumb, 피드·상세는 original이다. 조회 사진은 메모리에서만 관리하고 계정 변경 시 비운다. 이미 합성된 사진에 물감·자르기를 다시 적용하지 않는다.
- 사진 404·조회 실패·재시도·작은 격자의 오류 표시를 처리한다. 로그인 맛보기의 흐린 장식 배경은 로딩·통신 실패·이미지 해독 실패 시 아무것도 표시하지 않는다. 재시도 응답이 너무 빨리 실패해도 화면 구독 전의 미처리 오류가 되지 않도록 한다.

## 실제로 검증한 범위

- Windows의 Android 17(API 37) 에뮬레이터와 실제 로컬 Docker 서버·DB 사용. Mock 전환 없음.
- Android에서 앱의 업로드 모듈로 그대로·물감·목 아래 PNG 업로드 → READY → 원본·썸네일 조회. 1080×1440 결과 확인, 원본 사진을 그대로 보낸 것이 아님을 검사.
- 다른 계정은 미발행 사진에 404, 원래 계정 재로그인 후 동일 바이트 재조회, 존재하지 않는 사진의 404 확인.
- 정상 앱에서 이메일 로그인, 홈·팔레트 색 방·마이페이지 격자·세로 스케치북·상세 사진 표시, 본인 표지 이동 확인.
- 사진 선택·취소, 얼굴을 눌러 물감 위치 변경, 목 아래 전환과 물감 비활성화, 전체 미리보기·뒤로가기, 키보드·문구 입력·초안 저장 확인. 앱 강제 종료 후 사진·문구·목 아래 연출 복원 확인.
- 사진 권한 거절·선택 취소·선택 파일 누락 시 기존 초안 보존은 플러그인 실패 응답을 주입한 자동 위젯 검사로 확인했다. Android 17의 실제 시스템 사진 선택기는 선택한 사진만 접근하며 별도 앨범 권한 대화상자는 표시되지 않았다.
- 자동 검사: Flutter analyze 통과, 일반 테스트 **272개 통과·실서버용 2개 기본 건너뜀**. 별도 명시한 media 실서버 검사 1개 통과. 규칙 검사 60개, 하네스·생성·빌드 검사 통과.
- 디자인 캡처 검사 28장은 별도 임시 출력으로 실행해 기존 팀 디자인 이미지를 덮어쓰지 않았다. 이번 실제 Android 증거는 아래에 둔다.

사진 조회 화면용 테스트 게시물은 전용 계정에 **기존 서버 API로 직접 준비**했다. 이는 #31 앱 발행 버튼이 완성됐다는 의미가 아니다. 기존 사용자 기록이나 DB·사진 볼륨은 삭제하지 않았다.

## 실행·재현

Flutter 3.44.0 / Dart 3.12.0. 새 패키지·서버 endpoint·migration 추가 없음.

```sh
docker compose up -d --build api
cd flutter_app
flutter pub get
flutter run -d <android-device-id> --dart-define=ESEL_API_MODE=server --dart-define=API_BASE_URL=http://10.0.2.2:3000/api
```

위 명령은 Windows·macOS의 Android 에뮬레이터용이다. USB Android는 `adb reverse tcp:3000 tcp:3000` 후 API_BASE_URL을 `http://127.0.0.1:3000/api`로 사용한다. 경로는 저장소 기준이며 개인 PC 절대 경로를 요구하지 않는다.

실제 미디어 모듈 검사는 `test/features/media/media_live_test.dart`다. **전용 로컬 검수 계정만** 사용한다. 별도 비공개 JSON에 `baseUrl`(127.0.0.1의 API), `owner`·`reader`(각 email·password)를 두고 ESEL_MEDIA_FIXTURE 환경변수로 경로를 지정한 뒤 `flutter test test/features/media/media_live_test.dart`를 실행한다. 준비한 계정에 테스트 사진을 추가하며 기존 데이터를 지우지 않는다. 비밀번호·토큰·fixture·임시 검수 앱은 커밋하지 않는다.

## 보류·후속 작업

1. **사인 뒤로 업로드:** 맨 위 얼굴 노출 문제에 관한 팀 합의 필요. 다른 사진 모듈이 통과해도 해제하지 않는다.
2. **#31 실제 캔버스 발행:** 서버의 faceCrop + paintStroke 저장 계약 변경 후 진행한다. 현재 발행 버튼은 준비 중 안내를 유지한다. 업로드 모듈이 있다는 이유로 실제 발행까지 완료했다고 쓰지 않는다.
3. #31에서 완료 mediaId로 POST /issues, 서버가 준 옷 UUID만 사용, 옷 좌표 변환, 409·MEDIA_NOT_READY 안내, 성공 후 오늘 상태·스케치북·피드 재조회를 연결한다. 현재 서버 구조·데이터는 보존했다.
4. Android 실기기·macOS·iOS는 미검증이다. 실제 권한 대화상자 거절과 파일 삭제 상황의 기기별 차이도 후속 확인이 필요하다. 현재 근거로 모든 기기에서 문제없다고 보장하지 않는다.

## #32 리뷰 반영과 #31 시작 전 점검

최신 main을 작업 브랜치에 반영했다. 충돌 난 사진 테스트 도우미와 서울 2026-10-18 정오의 고정 시계를 모두 유지하고 관련 오늘 상태 테스트 3개가 같은 시계를 사용하게 했다.

- 로그인 전 흐린 배경은 통신·해독 실패 안내와 재시도 버튼을 숨긴다. 일반 사진의 안내·재시도는 유지한다.
- 발행 콜백 유무로 시연 모드를 추측하지 않는다. 앱이 선택한 데이터 모드를 편집기에 전달하며 mock 모드에서만 로컬 시연 발행 안내를 표시한다. 발행 없는 초안 편집은 기기 보관 안내를 유지한다.
- 이번 리뷰 수정 후 전체 Flutter 테스트 **278개 통과·실서버용 2개 기본 건너뜀**, 정적 분석 통과. 추가한 6개 검사는 장식 배경의 404·통신·해독 실패와 mock/server 발행·발행 없는 초안 안내를 확인한다. 이후 아래 Android 화면 검수를 추가했다. 위의 Docker 검수는 최초 #32 작업 때 수행한 기록이며 이번 문구·배경 수정 후 Docker 전송 검사를 다시 수행했다는 뜻은 아니다.

리뷰에서 아래 3개는 **이번 수정 범위에서 제외하고 #31 착수 전에 처리**하도록 정했다. 현재 해결되었다고 보지 않는다.

1. 업로드 시간 제한: 현재 본문 전송까지 15초 제한에 포함되어 느린 모바일에서 실패할 수 있다. 전송에 맞는 제한·진행 처리와 느린 전송 테스트를 정한다.
2. PNG 용량: 효과 적용 사진의 JPEG 변환을 검토한다. 파일 크기·화질·얼굴 가림 결과를 비교하고 형식 변경 시 서버 허용 형식도 함께 확인한다. 원본 업로드로 우회하지 않는다.
3. 디코딩 크기: 원본 전체 해상도를 읽어 메모리가 늘 수 있다. 최대 가로 2160 정도를 검토하되 회전·세로 사진·물감 위치를 함께 확인해 제한을 결정한다.

사인 뒤로 서버 업로드 차단과 #31 발행 연결 보류는 위 점검과 별개로 계속 유지한다.

## #32 수정 후 Android 실제 화면 검수

2026-10-19, 앱 코드 `fe4a888`. Windows의 Android 17(API 37) 에뮬레이터에서 직접 조작하고 화면 캡처를 확인했다. 기본 1080×2424, 420dpi 및 작은 화면 960×1600(논리 폭 약 366dp)에서 확인했다. 이번 추가 작업은 검수 기록·캡처만 추가하며 제품 동작을 바꾸지 않는다.

방법: 임시 Android 진입점에서 제품의 `IntroScreen`·`PublishScreen`·`CoverEditorScreen`을 그대로 사용했다. 실제 `EselApp`에는 메모리 시연 계정·초안을 넣어 ‘만들기’와 ‘설정 → 기기 초안 → 재편집’ 경로를 눌렀다. 사진 실패는 검수 전용 HTTP 대체 응답으로 404·통신 오류·이미지로 읽을 수 없는 바이트를 재현했다. 서버용 편집 안내는 동일 제품 편집기에 서버 모드 표시 값을 전달해 비교했다. 실제 Docker 장애·서버 로그인·업로드를 다시 검증한 것은 아니다. 임시 진입점·계정·메모리 자료는 제품 코드나 커밋에 포함하지 않는다.

| 직접 확인한 화면·동작 | 결과·증거 |
|---|---|
| 비로그인 마지막 안내의 사진 404 | 흐린 배경은 비워지고, 배경 안 오류·재시도 버튼이 나타나지 않음. 작은 화면에서도 로그인 바와 안내를 확인. [404 화면](screens/media-upload/review-intro-404.png) |

| 일반 사진 오류와 배경 오류 구분 | 위 두 캡처 맨 위의 ‘사진 다시 보기’는 앞쪽 일반 사진의 안내다. 마지막 안내의 흐린 배경에는 표시되지 않음. 일반 사진 재시도 UI를 없앤 것이 아님 |

확인한 화면에서 크래시·레이아웃 넘침이나 안내 겹침은 발견하지 못했다. 작은 화면에서는 긴 앱 바 제목이 말줄임되며 본문 안내는 읽을 수 있었다. 확인하지 않은 실기기·macOS·iOS와 전체 서버 흐름까지 정상이라고 확대해 설명하지 않는다. 사인 뒤로 서버 업로드 차단과 #31 시작 전 성능 보완 3개는 유지한다.
