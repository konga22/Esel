# 오늘의 캔버스 실제 발행 연결 (#31)

## 확정 범위와 보류 이유

2026-10-19 추가 팀 결정: **서버의 얼굴 연출 저장 칸 변경을 기다리지 않는다.** 사인 뒤로와 사인 뒤로+물감은 업로드를 차단하므로 남은 연출은 기존 서버 DTO로 모두 표현된다.

| 앱 연출 | 기존 서버 faceMode |
|---|---|
| 그대로 | PLAIN |
| 그대로+물감 | PAINT |
| 목 아래(물감 자동 해제) | NECK_DOWN |
| 사인 뒤로 / 사인 뒤로+물감 | 파일 읽기·업로드 전에 SIGNATURE_UPLOAD_PENDING으로 거절 |

사인 글자·캡션을 뺀 사진에서 얼굴이 다시 드러날 수 있어 사인 뒤로 차단을 유지한다. 임의로 PLAIN이나 PAINT로 바꿔 보내지 않는다. 로컬 시연과 기존 저장본의 얼굴 연출은 보존한다. 이번 주 주제·전시·트윈의 서버 연결과 새 endpoint·DB migration은 추가하지 않았다.

## 동작

- 기존 `TodayController.publish`를 공통 진입점으로 사용한다. 실제 계정·오늘 상태를 다시 읽고 선택한 후보 색을 저장한 뒤 사진 합성 → 준비 POST → 사진 PUT → 완료 READY → POST /issues를 호출한다.
- 서버 발행은 `PublishingRemoteSource`로 분리했다. 완료된 mediaId, 문구, 기존 faceMode, 최대 8개 착용 정보를 보낸다. 공개 숫자·순위 필드는 추가하지 않았다.
- 로컬 옷 ID(micros-rand)는 garmentId로 보내지 않는다. UUID라도 GET /me/garments의 실제 본인 목록에서 확인되고 종류·이름·메모가 같은 옷만 재사용한다. 목록 응답의 키는 id다. 달라진 옷 정보는 새 옷으로 보낸다.
- 원본 사진의 옷 좌표를 합성된 1080×1440 사진 기준으로 옮긴다. 잘려 화면 밖으로 나간 점은 좌표를 빼되 옷 목록은 남긴다. 상세에서는 서버가 준 옷 목록과 사진 태그를 표시한다.
- 발행 중 중복 호출을 막고 계정이 바뀐 응답은 현재 계정에 적용하지 않는다. 409 ISSUE_ALREADY_PUBLISHED·MEDIA_NOT_READY 등 기존 서버 오류를 안내한다. 실패한 사진을 원본이나 Mock으로 대신 보내지 않는다.
- 발행 응답을 받으면 오늘 상태·호수를 반영하고 재조회한다. 그 뒤 조회만 실패해도 이미 완료한 발행을 실패로 되돌리지 않는다. 홈·스케치북도 다시 읽는다. 새 시도 전에 오늘 상태를 재조회해 이전 요청의 응답을 놓친 경우에도 중복 생성하지 않는다.
- 기기의 초안·원본 사진은 지우지 않는다. 서버 발행과 기기 초안은 별개이며, 남은 초안으로 오늘 다시 올리려 해도 서버의 하루 한 호 규칙을 통과해야 한다. 로컬 시연의 호수·기록 저장 방식은 그대로다.

## 사진 처리 보완

### 느린 업로드

기존 본문 전송을 포함한 15초 제한을 사진 PUT에서는 **30초 + 사진 크기 / 초당 32KiB**의 유한한 예산으로 바꿨다. 3MiB는 126초, 허용 최대 15MiB는 510초다. 크기를 넘겨 입력해도 예산이 계속 커지지 않는다. 연결 제한 10초, 응답 수신 무진행 제한 15초, 일반 JSON 요청 15초는 유지한다. 무한 대기는 아니다.

실제 로컬 HTTP 서버가 3MiB 본문을 16초 후 읽도록 한 자동 검사를 통과했다. 실제 이동통신망의 모든 속도·끊김 상황을 확인했다는 뜻은 아니다.

### 디코딩

사진 선택 시 maxWidth·maxHeight를 2160으로 요청한다. 기존에 저장한 큰 사진도 업로드 합성 전에 ImageDescriptor로 크기를 확인하고 **긴 변 2160 이하**로 디코딩한다. 작은 사진은 확대하지 않고 비율을 유지한다. PNG 출력은 1080×1440을 유지한다. 가로·세로 4320 사진과 작은 사진으로 실제 디코딩 크기를 검사했다.

### JPEG 비교 결과 — 출력 전환은 미적용

저장소의 예시 사진 `sage-01.jpg` 한 장을 실제 앱 렌더러로 합성한 결과 3종을 측정했다. 동일 1080×1440 결과를 Pillow의 JPEG 품질 90·4:4:4·optimize로 변환한 **개발용 비교**다. Pillow를 앱 의존성으로 넣지 않았다.

| 연출 | 현재 PNG(bytes) | 비교 JPEG(bytes) | 감소 | PSNR(dB) |
|---|---:|---:|---:|---:|
| 그대로 | 1,175,895 | 219,518 | 81.3% | 48.7 |
| 물감 | 1,188,112 | 223,517 | 81.2% | 48.1 |
| 목 아래 | 1,194,839 | 215,772 | 81.9% | 49.4 |

용량 감소 가능성을 확인했다. 다만 표본은 사진 한 장에 연출 세 가지이며 전체 사진의 평균이 아니다. PSNR은 픽셀 차이 측정이고 사용자 선호나 익명화 보장 수치가 아니다. 물감 JPEG도 직접 열어 확인했지만 모든 얼굴·회전·색 공간의 품질 검수는 하지 않았다.

**현재 앱 업로드는 PNG를 유지한다.** 기존 Flutter 렌더러의 PNG 출력 외에 JPEG를 넣으려면 승인되지 않은 새 인코더 패키지 또는 별도 네이티브 구현이 필요하다. 새 라이브러리를 임의 추가하지 않는 기준을 지켰다. JPEG는 비교 검토를 완료한 것이며 앱의 JPEG 변환까지 구현했다고 표시하지 않는다. 모바일 인코더 선택 후 허용 MIME·메모리·물감 경계·회전 사진을 추가 검수하는 작업이 남는다. 원본 JPEG를 대신 올리는 우회는 하지 않는다.

## 실행

기존 Flutter 3.44.0 / Dart 3.12.0 및 Docker 구성을 그대로 사용한다.

```sh
docker compose up -d
cd flutter_app
flutter pub get
flutter run -d <android-device-id> --dart-define=ESEL_API_MODE=server --dart-define=API_BASE_URL=http://10.0.2.2:3000/api
```

Android USB는 adb reverse tcp:3000 tcp:3000 후 API_BASE_URL=http://127.0.0.1:3000/api를 사용한다. Windows·macOS에서 Android 개발 시 같은 상대 경로 명령을 사용한다. macOS·iOS·실물 Android 실행은 미검증이다.

## 검증 범위

- 전체 Flutter 테스트 297개 통과, 실서버용 3개 기본 건너뜀. 정적 분석 통과. 발행 값 3종·사인 뒤로 차단·로컬 옷 ID 제외·본인 UUID 확인·좌표 변환·409·MEDIA_NOT_READY·계정 변경·이중 호출·발행 후 조회 실패·서버 사진 태그 터치도 검사했다.
- 별도 로컬 Docker 실발행 검사 1개 통과: 전용 계정으로 연출 3종을 각각 실제 발행, 옷 UUID 생성·목록 키 id, 피드·본인 스케치북, 원본 사진 재조회, 당일 재발행 거절, 로그아웃·재로그인 후 같은 기록·사진 조회. 테스트 계정·게시물만 추가하고 기존 자료는 지우지 않았다.
- Windows / Android 17(API 37) 에뮬레이터: 실제 제품 EselApp과 실제 서버 API를 사용했다. 임시 진입점에서 검수 계정으로 이메일 API 로그인하고 전용 기기 보관함을 연결했다. 일반 사용자의 세션 저장소는 덮어쓰지 않았다.
- 실제 시스템 사진 선택기로 사진 선택 → 얼굴 연출 확인 → 초안 저장 → 실제 올리기 → 내 스케치북 1장 → 상세 문구·착용 정보 표시 확인. 사인 뒤로 차단도 실제 버튼으로 확인했다. 앱 완전 종료 후 재로그인·홈 사진 조회와 당일 두 번째 만들기 차단을 확인했다.
- 갤러리에서 돌아와 사진을 바꾸면 얼굴 확인 체크와 옷 좌표가 해제되는 기존 규칙을 확인했다. 임시 에셋 참조 사진은 파일 존재 검사에서 거절되는 것도 확인했고, 실제 갤러리 파일로 발행했다. 이 거절을 서버 장애로 처리하지 않았다.
- API 컨테이너만 재시작한 뒤에도 같은 게시물·호수·사진 SHA-256이 유지되는 것을 확인했다. DB와 영구 볼륨은 삭제하지 않았다.
- 검수 도중 서버 업로드 진행을 ‘기기에 저장 중’이라고 표시하던 문구를 발견해 서버·로컬 모드별로 구분했다. 예외 안내도 서버 연결 오류에 맞췄다.
